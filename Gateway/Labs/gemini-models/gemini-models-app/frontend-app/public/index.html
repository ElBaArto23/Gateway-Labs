Este diagrama se anima solo con tráfico real: en cuanto mandas un mensaje de verdad, el punto recorre el camino real y muestra el resultado real (ms, tokens, x-debug-key-source).

Sin actividad todavía en esta sesión — manda un mensaje real desde "Probar Gateway" para ver el flujo aquí, en vivo.

Qué pasa en cada salto

  1. Eliges una unidad de negocio y escribes un mensaje en "Probar Gateway"; el navegador manda POST /api/chat al backend — nunca directo al gateway.
  2. El backend (server.js, en Azure App Service) lee del App Setting la subscription key de APIM que corresponde a esa unidad de negocio y arma la llamada con el header Ocp-Apim-Subscription-Key.
  3. La llamada llega a API Management (apim-shared-pdcibwky2f5ms), la instancia compartida con otros labs. APIM valida la subscription contra gemini-models-subscription1/2/3.
  4. APIM resuelve la Named Value con la API key real de Gemini para esa unidad de negocio (cada una en su propio proyecto de Google Cloud) y reenvía el request a la API de Gemini.
  5. Gemini responde; APIM agrega el header de diagnóstico x-debug-key-source (por ejemplo gemini-models-key-subscription1) confirmando qué Named Value se usó, y devuelve la respuesta.
  6. El backend reenvía el contenido, el modelo usado, los tokens y el tiempo de respuesta al navegador, que actualiza el chat y las métricas de esa unidad de negocio.

🔒 Ni la subscription key de APIM ni la API key real de Gemini llegan nunca al navegador: viven solo como App Settings del backend y como Named Values dentro de APIM.

La ruta gris punteada del diagrama (v1) era el playground original, que llamaba al gateway directo desde el navegador y por eso necesitaba CORS en gemini-shared-resources.bicep. Con el backend de App Service en su lugar, esa política queda pendiente de revisar — ver sección 7 del informe de avance.
